# Supabase integration
The active migrations match hosted database history. The initial 0001–0005 prototypes are archived under docs/legacy-supabase-schema and must not be deployed; they predate the current domain and security review.

The publishable key in supabase-public.json is intentionally public and limited by RLS; never put a secret/service-role key there. GitHub Pages and the health workflow use it by default. Optional existing VITE_SUPABASE_URL and VITE_SUPABASE_ANON_KEY secrets override both. Local dev defaults to unconfigured unless environment variables are supplied. Health workflow runs three times daily; automatic pausing is not guaranteed to be prevented, and public GitHub schedules may disable after 60 days of repository inactivity.

The current milestone includes private, immutable cloud backup snapshots and JSON export/import for individual tournaments, not cloud-authoritative live operation. Cloud snapshots contain sensitive participant names/codes, are owner-only, and can be explicitly deleted. Restore refuses to overwrite any local tournament ID. No synchronization occurs. Supabase email authentication may require configuring the GitHub Pages site URL, allowed redirect URLs and SMTP in the dashboard. The next milestone is a versioned, server-authoritative command API, shared domain validation and transaction handling, not automatic replication of browser storage.

Hosted schema tested with two synthetic account IDs inside a rolled-back transaction. No test users or rows remain. Current database health probe uses invoker rights and a non-sensitive read-only marker. For local resets use only the active migrations, not the archived prototypes.

## Experimental online workspace
Online events use a separate in-memory compatibility adapter (no local tournament IndexedDB writes) and a hosted versioned snapshot RPC. Unstarted local events can be copied into a private online test event. Each write uses a per-event transaction, expected revision and idempotency key; conflicts or unconfirmed commits stop further edits and require reload. The UI blocks interaction during pending commits. PostgreSQL is authoritative for persisted snapshots, not yet for individual domain commands. Local and online copies do not synchronize. The next steps are direct online creation, deeper domain validation on the server, concurrency and recovery UX, and complete end-to-end acceptance tests. No live release yet. The private schema intentionally has RLS with no direct table policies or grants; authenticated RPC wrappers are invoker functions calling explicitly owner-checked private functions.

Direct online creation now uses the same validated tournament constructor as local creation, but never writes a local tournament record. The server validates the full envelope, header, participants, stages, and tournament scope of every runtime collection before committing. This does not validate sport-specific actions or score transitions. Retry within an open wizard retains the original operation UUID and payload; after a browser reload inspect the online catalog before creating again. Multi-day mode and planned day count are persisted by both creation paths.

## Interrupted online writes
The online workspace blocks edits while the browser reports offline. A commit with an ambiguous transport response keeps its exact snapshot and operation UUID in memory, blocks edits, and offers explicit retry. A confirmed retry reopens the director; a revision conflict is never automatically overwritten. Unconfirmed snapshots can be exported as private JSON for manual reconciliation. Leaving the page discards in-memory recovery, with a browser unload warning. This is not a durable offline outbox. Unit integration tests exercise completion across independent module instances, not two real authenticated browser sessions.

## Durable recovery and checkpoints
Each confirmed revision is checkpointed transactionally, bounded to 20 revisions and 16 MiB logical JSON per event. Only its owner can list and export a checkpoint. Restore is intentionally offline and non-overwriting; no rollback of the current cloud revision. Runtime writes first persist the exact payload, expected revision and operation UUID in a separate IndexedDB journal scoped to account and tournament. On reopening, unresolved entries block the director and require explicit idempotent retry or discard. The journal contains private tournament data on this browser; it is not encrypted against users with local browser access. Do not use shared unmanaged devices. Initial creation still uses its separate in-memory retry path.

Runtime SQL guards reject duplicate match records, unknown phase references, inconsistent completion lists, malformed scores, invalid table numbers, simultaneous active table assignments and terminal status resets. They are not a full server-side implementation of sport rules; client pairing, qualifiers and detailed correction rules remain authoritative only within the private test workspace.

Creation now also journals revision-zero operations before transport, including copies of local tournaments. The online catalog lists unresolved creations even if the server has not received them. Reopening that link permits exact retry or explicit discard before normal workspace boot. A saved wizard draft can remain after crash recovery; it is not automatically deleted across reloads.

Sport scoring checks now enforce valid sets, best-of, decisive set limits, score-mode cardinality and winner-required ties, using the existing client rules (not an independent official sport rulebook). Bronze Best-of accepts configured candidates until exact bracket validation moves server-side. Administrative withdrawals and skipped bronze matches still require separate domain validation; detailed tiebreak metadata and qualifier computation remain client-side. The backup RLS predicate was optimized.

The server now freezes sporting content of completed results when a dependent round/competition is already started, while permitting review flags to change. CI additionally replays real client-generated snapshots for three event types through the complete migration chain in PostgreSQL 17 with synthetic Supabase auth helpers. This is not a full authenticated hosted-browser test. The CI runner is pinned to Ubuntu 24.04 to avoid transient package repository failures on the latest image.

The director checks the event revision on focus, reconnect, every 30 seconds in a visible tab and on demand. No automatic merge or replacement occurs. If a newer revision is detected, interaction is frozen until reload. Failed metadata checks show uncertainty; the atomic revision check still protects all writes. This is not a distributed edit lease.

Safety review: stale revision detection freezes the storage facade itself. If multiple queued mutations precede a failed write, the latest cumulative snapshot is available for manual JSON export, while exact retry is deliberately disabled. Only the operation actually journaled before transport survives a crash; the additional cumulative state must be exported before leaving the page. It is not safe to automatically rebase a conflicting sporting result.

## Exclusive director workspace
Every update now requires a private event-scoped token and a live 90-second lease, renewed every 20 seconds and on successful commits. Acquisition, release and writes share the same database transaction lock. The old five-argument RPC supports creation only, never a runtime write. A second tab/device is blocked at open, until the first explicitly releases or its lease expires. An ordinary reload or crash may require waiting for expiry; the explicit release-and-back button avoids this. Recovery obtains a fresh lease before replaying journaled updates; idempotency and revision checks still apply. No automatic forced takeover. Hidden tabs may be throttled. This is an exclusive editor, not a read-only public viewer.

## Online catalog and archive
Owner-only catalog exposes status, archive timestamp and lease state (not lease tokens). Archiving is reversible metadata and does not increment sporting revisions or discard checkpoints. The event lock serializes archive with claims/commits, and active leases and running/paused events cannot be archived. Archived events cannot acquire an editor lease. Confirmed JSON export is read-only. The backup envelope now rejects missing required fields on new inserts. Existing backup rows are preserved.

## Unlisted spectator preview
Explicit opt-in in the online catalog creates a random UUID capability. The public read RPC constructs a fixed projection from the current confirmed database revision; it never exposes the snapshot, participants, credentials, lease tokens, or operation journal. It shows tournament/phase names and aggregate progress only. Revoking, rotating or archiving invalidates the link. Previously observed information cannot be recalled. The public page polls every 15 seconds and clears the last view on failure/revocation. No player login, standings, per-match public data or public writes yet. Links use a hash fragment; no public directory.

## Optional spectator match details
Separate default-off consent per link. Link rotation resets detail consent. The active director derives started-phase fixtures using existing runtime functions only from a quiescent confirmed revision; publish occurs on initial open and periodic revision checks. The database checks ownership, current lease, current revision, roster names and a bounded allowlist. The projection is hidden whenever a revision changes until republished. At most 1,000 rows (live and finished prioritized), no internal identifiers or codes. This is a client-generated presentation, not independent server-side pairing verification. If no director is open, details may remain unavailable for a new revision. Do not publish participant names without permission.

### Spectator rankings
The same explicit detail consent enables group, round-robin, Swiss and confirmed overall placements. Existing tournament ranking functions produce the rows; no separate public recalculation. The server validates allowed fields, roster membership, unique names per table, size, current revision and lease. Disable/rotate/archive remove the projection. At most 200 tables and 5,000 rows (1 MiB), no silent truncation; oversized publication fails. Like match projections, ranks are presentation data, not an independent server-side verification of sporting calculations.

### Spectator brackets and personal filter
Started knockout phases publish round-ordered brackets, structured participant/bye/pending slots, scores, sets and winner side only, with the same lease and revision checks. Maximum 2,000 bracket matches and 1 MiB. A public participant selector filters already released matches by exact name; it is not a private player login. Hash-only spectator link navigation reloads the isolated boot and cannot retain the previous token.
